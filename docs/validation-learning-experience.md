# Learning experience validation

## Diagnosis and scope

The existing six command-line tools were functional, but users had to infer how templates, actions, indicators, and reports connect. Priority HIGH: add a problem-based entry point and a reproducible tutorial. Priority MEDIUM: standardize module instructions and report guidance. Existing CSV schemas and automation were retained; report templates were centralized instead of duplicated under document control.

The learning path is Start Here → select a problem → read one module → run the fictional tutorial → interpret outputs → assign and verify actions → select a report template.

## Reproduction

From the repository root, install pytest as described in [Getting Started](getting-started.md), then run:

```text
python -m pytest -q
```

The [tutorial](tutorials/first-improvement-cycle.md) contains the exact scenario commands. The three published CSV outputs in [expected](../examples/first-improvement-cycle/expected/) were generated by those scripts and are checked by [regression tests](../tests/test_learning_examples.py). Expected inventory exit code 1 demonstrates an overdue inspection, not a failed tutorial.

## Interpretation and limits

TESTED AUTOMATICALLY: CLI calculations, validation behavior, and published CSV fixtures. Reviewed manually: learning sequence, module boundaries, report structure, evidence labels, and traceability guidance. NOT TESTED IN HARDWARE: the scenario is fictional and contains no measured improvement or physical validation.

No production script was changed. Reports are manually authored Markdown; PDF/Word export, approval workflows, source-ID joins, and report generation are not implemented. Future expansion should follow [the roadmap](../ROADMAP.md): richer process analysis, configurable rubrics, additional quality templates, optional analytics, and institutional report adaptations.
